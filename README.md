# Throughline web (ai-owning-sdlc-web)

UI for the AI SDLC platform: one product that takes rough ideas to running software, with human gates, agents doing the work, and proof for every change. Multi-tenant from the first line of code.

> **Status:** UI-first. The app runs entirely against an in-browser mock API (MSW) with three sample workspaces, so you can click through it with no backend.

## Run it

Needs Node 22.12+ and pnpm 10 (`corepack enable` gives you the pinned version).

```bash
pnpm install
pnpm dev            # http://localhost:5173 — mock API, sample data
```

Other commands:

| Command                       | What it does                                                                                                                            |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm check`                  | Lint (with design-token rules), typecheck and all tests                                                                                 |
| `pnpm build` / `pnpm preview` | Production build and local preview (mock API still on)                                                                                  |
| `pnpm dev:live`               | Turn the mock off and proxy `/api` to a real API: `API_URL=http://localhost:8000 pnpm dev:live`. Other settings: `apps/web/env.example` |
| `pnpm lint:fix`               | Format and auto-fix                                                                                                                     |

### The journey

`/` landing page → **Sign in** (`/login`) → **Choose a workspace** (`/workspaces`) → the app (`/t/<workspace>/…`).

- Sign-in is mocked: any of the SSO buttons, or any work email, signs you in as Priya. Real OIDC goes through a backend-for-frontend later; the screens don't change.
- Every app page requires sign-in. Open a deep link while signed out and you're sent to `/login`, then straight back afterwards (only to in-app paths, so `/login` can't be used as an open redirect).
- Sign out from the account menu (top right). It clears every cached workspace's data.

   | Fabrikam Retail | US · pooled             | viewer                       | Can't approve anything; read-only everywhere        |
2. **Control room:** click stages on the lifecycle; approve a gate decision (only where your role allows); **Review evidence** opens the exact item.
3. **Approvals:** every sign-off waiting on you (gates, BRDs, test plans) in one queue; **⌘K** jumps to any project, BRD or work item, or asks the assistant.
4. **Programs & projects:** every BRD, architecture, plan, backlog and work item belongs to a project, and projects sit in programs. Open a project (e.g. Acme SUP or MCP) for its lifecycle, Gantt plan with cross-project milestones, artifacts and traceability; the top-bar project picker narrows BRD and Architecture to that project. The **Work items & trace** tab follows any work item through every stage and tool.
5. **BRDs & specs → Specs · G1**, **Architecture → Design options**, **Delivery → Build / Verify · G3 / Release · G4**: the stage screens now live as views of these pages.
6. **Settings → Integrations / Security:** toggle write-back and controls (Acme), then switch to Fabrikam and see the same page read-only.
7. **Switch workspace** from the top-left. Data, permissions and cache all change with it.

## Multi-tenancy: how it works

Tenancy is enforced at five layers so that a mistake in one is caught by the next.

1. **Routing boundary.** Every signed-in screen lives under `/t/$tenantSlug`. That route resolves the tenant from the session and returns **404** if you're not a member (unknown and forbidden look identical, so ids can't be probed). Subdomains are supported too: set `VITE_TENANT_BASE_DOMAIN=throughline.app` and `acme.throughline.app` redirects into `/t/acme`.
2. **Tenant-scoped API client.** Feature code never calls `fetch`. It uses `useTenant().api`, which puts the tenant id in the path (`/api/t/{tenantId}/…`) **and** the `X-Tenant-Id` header. Responses are validated against the shared zod contract.
3. **Tenant-scoped cache.** Every query key starts with `["tenant", tenantId]` (`useTenant().keys`). Two tenants can never share a cache entry, and a tenant's cache is dropped when you leave it.
4. **Permissions from the server.** The session lists `allowedActions` per membership. The UI shows or hides actions with `can()` / `<Can>`, but the API is what enforces them (403).
5. **Server guard (mirrored in the mock).** `src/mocks/guard.ts` is the contract the real API must implement: well-formed id, header matches path, caller is a member, action allowed. `src/mocks/isolation.test.ts` proves it.

The real backend still owns the hard parts: per-tenant databases or row-level security, per-tenant encryption keys, and per-tenant agent sandboxes and memory.

## Design system

- Two themes: dark (default) and a neutral light theme, switched from the sun/moon menu in the top bar or studio header (or "Match system"). The public landing and sign-in pages stay dark. Unbounded (display), Geist (UI), Martian Mono (data); fonts are self-hosted.
- Colour has fixed meanings: **agent** (mint) = agents and movement, **gate** (amber) = a person decides, **ion** (blue) = secondary flow, **ok** (green) = verified, **risk** (red) = danger.
- Use only semantic classes (`bg-surface`, `text-muted`, `text-agent`, `text-heading-md`…). Lint rejects raw colours, Tailwind palette classes and arbitrary sizes.
- Motion means something: shimmer = agent working, pulse = live, flowing dash = work moving, pop = approved. Everything respects reduced-motion.
